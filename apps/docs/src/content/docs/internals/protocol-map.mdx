## 导读：先问它替谁解决什么问题

看到 TCP、UDP、STUN、QUIC、Noise 一起出现，很容易以为它们是同一组“连接模式”。其实，它们可能出现在不同位置，有的负责应用对话，有的搬包，有的寻找入口，有的证明身份。选项名字相近，不表示它们能互相替换。

这一篇以 A `10.144.144.1` 访问 B `10.144.144.2:8080` 为主线，R `10.144.144.254` 可以帮助转发。先读[第 4 章：协议与端口](/chapters/04-protocols)、[第 7 章：TUN](/chapters/07-tun)和[第 15 章：完整请求](/chapters/15-journey)。读完后，你应能把一个协议放到正确位置，并说明单独看到它还不能证明什么。

下面的协议能力以 **EasyTier v2.6.4** 为准；图是教学模型，不是实际抓包。公网端点 `198.51.100.10`、`203.0.113.20` 和 `192.0.2.10` 是文档保留地址。

## 直觉：同一份请求可以有两套运输规则

A 的浏览器说“我要读 B 的网页”，使用 HTTP（超文本传输协议）表达方法、路径和回答。我们选择传统 HTTP over TCP 示例：TCP（传输控制协议）负责可靠、有序的字节流，IP（网际协议）负责把包送向目标地址。

系统把目标虚拟 IP 的包交到 TUN（在系统与用户态程序之间交接 IP 包的虚拟接口）。EasyTier 再把整个内层 IP 包作为载荷放进自己的协议包，通过原有网络发走。外层可以选 UDP（用户数据报协议），内层 TCP 的连接状态仍在 A、B 的操作系统里。

**阅读顺序：**先沿 A 到 B 读内层，再向下看它如何被外层承载，最后寻找两层分别使用的地址。**结论：**外层协议变化，不会自动改写内层业务协议；一台电脑也会同时参与多种协议。

## 第一步：用五元组给一次通信定位

五元组是“源 IP、源端口、目标 IP、目标端口、传输协议”的组合。示例内层是：`10.144.144.1:53124 → 10.144.144.2:8080，TCP`。53124 是系统分配的示例临时端口，8080 是 B 的服务端口。

若外层是 UDP，NAT（网络地址转换）后的端点可能为 `198.51.100.10:31000 → 203.0.113.20:32000，UDP`。两个五元组分别回答“哪个应用连接”和“哪段隧道运输”。即使两层恰好使用相同端口编号，也只是数字相同，不能混为同一个收发入口。

五元组主要用于 TCP、UDP 等带端口的通信。ICMP（互联网控制消息协议）没有 TCP 那样的服务端口，诊断时用类型、代码及标识等字段关联请求。不要为了凑齐五项而给 ping 编造一个“ICMP 端口”。

## 第二步：把常见网络协议放回各自位置

层次是职责地图，不是要求每个真实包都严格按一幅七层图排列。下表中的“位置”说明本教程会在哪里遇到它。

| 协议 | 解决的问题与层次 | 在 EasyTier 场景中出现在哪里 | 适用边界 |
| --- | --- | --- | --- |
| IP：IPv4 / IPv6 | 网络层寻址与转发 | 内层虚拟 IP 包；外层原有网络 IP 包 | 有地址不等于有路由、监听或允许规则 |
| ARP：地址解析协议 | IPv4 局域链路中寻找下一跳的链路地址 | 原有以太网或 Wi-Fi 网络 | 普通 TUN 交接 IP 包，不是把整个以太网广播域延伸过去 |
| NDP：邻居发现协议 | IPv6 邻居与路由器发现，使用 ICMPv6 | IPv6 链路与主机协议栈 | 不能把它当成 IPv4 ARP；TUN 也不是通用二层桥 |
| TCP | 传输层可靠、有序字节流 | 内层网页连接；`tcp://` 等外层隧道 | 内外两条 TCP 连接有各自握手、确认和重传 |
| UDP | 传输层保留报文边界、无需 TCP 握手 | UDP 应用、UDP 隧道、STUN；QUIC 和 WireGuard 的外层 | UDP 本身不保证到达、有序或自动重传 |
| ICMP / ICMPv6 | 网络层控制与诊断反馈 | ping、不可达及包过大等反馈 | ping 成功只验证这次 ICMP 条件，不能证明 TCP 8080 正常 |
| DNS：域名系统 | 应用层把名称转换为记录 | 节点 URL 解析、应用查名；可选 Magic DNS 需要 `magic-dns` 构建特性 | DNS 回答不保证目标服务可达；DNS 不只使用 UDP |
| DHCP：动态主机配置协议 | 普通网络中分配地址等配置 | 原有局域网可能使用标准 DHCP | EasyTier 的 `--dhcp` 虚拟地址自动分配需按自身实现理解，不代表透明转发 LAN 的 DHCP 广播 |
| HTTP | 应用层请求和响应 | 本文 B 的网页服务；某些连接器还用 HTTP 读取节点信息 | `http://B:8080` 是业务；连接器 HTTP 也不等于持续 HTTP 隧道 |
| TLS：传输层安全协议 | 为上层通信提供加密与身份验证机制 | HTTPS 应用、WSS 传输等 | 应用 HTTPS 与 EasyTier 节点加密有不同终点；身份判断还取决于验证策略 |
| STUN：NAT 会话穿越工具 | 应用层探测所见外部端点 | 建链前收集地址及 NAT 行为线索 | 不负责中继业务，也不保证其他目标可达 |
| UPnP：通用即插即用 | 本地网关发现和端口映射等 | 在网关支持并允许时辅助建立映射 | 需要设备与策略支持，不是所有上游 NAT 都能配置 |
| NAT-PMP：NAT 端口映射协议 | 请求本地网关建立端口映射 | 与 UPnP 类似的辅助映射入口 | 请求成功也不证明多层 NAT 的所有入口均已打通 |

ARP、NDP 和 DHCP 之所以列在这里，是为了说明它们与覆盖网络的边界。不要见到“虚拟局域网”这个口语名字，就认为所有二层广播协议都会原样跨节点搬运。

## 第三步：区分隧道、控制面与流代理

**数据面**搬运应用数据；**控制面**交换成员、拓扑、地址候选和连接状态等信息。两者可能共用现有连接，所以“隧道字节增长”也可能来自控制消息。

**图 2 · 按职责分类，比按名字长短分类更有用**

![协议家族分为应用通信、隧道搬运、建链与路由控制、安全身份、TCP 流代理；QUIC 同时出现在隧道和代理家族，KCP 只列为流代理。](/diagrams/protocol-families.svg)

[打开可缩放的 SVG 原图](/diagrams/protocol-families.svg)

**阅读顺序：**先看每一组解决的问题，再找到跨组出现的 QUIC，最后对照 KCP。**结论：**名字相同可以是不同能力，配置时必须继续问“在哪一层使用”。

| EasyTier 机制 | 职责与位置 | v2.6.4 使用位置及边界 |
| --- | --- | --- |
| TCP / UDP 隧道 | 数据面底层连接 | `tcp://`、`udp://`；把 EasyTier 包搬到相邻节点 |
| WS / WSS：WebSocket / 安全 WebSocket | 基于 TCP 的消息封装，WSS 再使用 TLS | `ws://`、`wss://`；需要 `websocket` 构建特性，不自动使内层应用变成网页协议 |
| QUIC：基于 UDP 的多路复用传输协议 | 一种外层隧道选择 | `quic://`；需要 `quic` 特性，与 QUIC TCP 流代理分别配置 |
| WireGuard | 一种受保护的 UDP 隧道机制 | `wg://` 节点传输需要 `wireguard` 特性；标准 WireGuard 客户端接入又是另一项能力 |
| FakeTCP | 使用 TCP 外观的特殊传输 | `faketcp://`；需要 `faketcp` 特性及对应平台能力，不等于普通 TCP 字节流 |
| KCP / QUIC TCP 流代理 | 代理虚拟网络内的 TCP 流 | `enable_kcp_proxy` / `enable_quic_proxy`，需要相应特性和对端能力；没有因此新增 `kcp://` 隧道 URL |
| 内部 RPC：远程过程调用 | 节点之间请求对方执行某项控制操作 | 成员、地址候选及拓扑等服务；与本机 CLI 管理 RPC 区别开 |
| 内部链路状态路由 | 控制面计算可用下一跳 | `peer_ospf_route.rs` 的命名借鉴 OSPF（开放最短路径优先）思路，不表示与标准 OSPF 路由器互通 |
| Noise | 安全握手框架 | `secure_mode` 中建立节点安全会话；不是所有默认加密连接都执行 Noise 握手 |
| ACL：访问控制列表 | 按条件允许或拒绝通信 | 授权；不能代替加密、入口身份验证或应用登录 |

## 怎样观察和核对

先在浏览器确认业务 URL，得到内层目标和端口；再看目标 B 的节点路径与连接协议；最后到原有网络接口观察实际外层端点。这三项证据各有位置，单独的“UDP”标签不可能完整描述网页访问。

<details class="advanced">
<summary>按源码辨认隧道与代理的入口</summary>

需要核对版本能力时，先读源码中的 `IpScheme` 和 `TunnelScheme`，再读 `gateway` 下的代理模块。v2.6.4 默认构建特性包含上述可选模块，但自行裁剪的二进制可能不包含；默认特性包含某功能，也不表示运行时已经启用它。

</details>

## 常见误解

“UDP 隧道里的 TCP 会失去可靠性”混淆了两层：内层 TCP 仍然确认和重传，只是运输可能丢包。“QUIC 就是 HTTP/3”混淆了传输与应用映射；EasyTier 使用 QUIC，不会自动把浏览器的 HTTP/1.1 改成 HTTP/3。“文件名有 ospf 就能与路由器跑 OSPF”忽略了私有控制消息与标准协议之间的区别。

## 两道练习与答案

1. 浏览器访问 `http://10.144.144.2:8080/`，GUI 里 B 显示 UDP。请分别写出业务协议、内层传输和外层传输。

<details class="answer">
<summary>查看第 1 题答案</summary>

本教程的业务是 HTTP，内层传输是 TCP，外层是 EasyTier 的 UDP 隧道。目标 B 的服务仍监听 TCP 8080；外层源、目标端口不必是 8080。

</details>

2. 开启 QUIC TCP 流代理，能否推断节点连接 URL 已变成 `quic://`，或 UDP 游戏也被同样代理？

<details class="answer">
<summary>查看第 2 题答案</summary>

都不能。TCP 流代理与相邻节点的隧道选择是不同位置，代理面向的是 TCP 流，不能把它的结果推广到所有 UDP 应用。还要检查对端接受能力和实际流量。

</details>
