## 导读：先把三个安全问题分开

“内容能不能被看见”“另一端是不是预期对象”“这个成员可以做什么”需要不同机制和证据。先读[数据面与封装](/internals/packet-pipeline)和[第 12 章：内容、身份与权限](/chapters/12-security)。本篇依据 **EasyTier v2.6.4**，以 A `10.144.144.1` 访问 B `10.144.144.2` 为例；R `10.144.144.254` 可以是同网成员，也可以换成不持有业务网络主密钥的公共共享节点，讨论时会明确区分。

**加密**保护内容，**认证**建立身份依据，**授权**限制操作。完成其中一件事，不能自动宣称另外两件也完成。EasyTier 节点间保护还与应用 HTTPS（使用 TLS 的 HTTP）具有不同终点。

## 第一步：网络名字、共同秘密与节点身份各管什么

网络名称帮助区分逻辑网络，它不是需要保密的密码，也不是全球注册、唯一认证的所有权证明。普通网络身份还包含网络密钥及其相关摘要；多个正式成员拥有共同秘密，意味着信任边界覆盖这些秘密持有者。

节点 ID 用于覆盖网络寻址，虚拟 IP 用于系统与业务通信，两者都不等于密码学身份。安全模式中的静态密钥对才提供长期节点身份材料：私钥必须保管，公钥可以公开，但必须可靠地关联到预期节点。

“公钥不保密”不等于“从哪里复制都可信”。公钥锁定需要先从可信渠道得到预期对象的公钥，再在建立连接时要求匹配。入口需保持稳定的私钥，否则重启后生成新身份，已有锁定配置就可能不匹配。

## 第二步：默认数据加密与安全模式不是同一个开关

v2.6.4 的常规配置默认启用数据加密。共享密钥路径根据网络秘密创建加密器，保护内层 IP（网际协议）包等载荷。AES-GCM（高级加密标准的 Galois/Counter 模式）等 AEAD（带附加数据的认证加密）算法会验证载荷完整性，而非只做可逆“乱码转换”。

这不表示所有默认连接都执行 Noise 握手。**`secure_mode` 是另一套节点安全会话与认证机制**：使用静态公钥、握手证明和目标会话，支持更细的认证状态、凭据和中继会话。把它说成“从明文切换到加密”会掩盖默认加密本来就存在，也掩盖认证与会话隔离的变化。

同网中继若持有共同主密钥，不能被当作毫无解密能力的旁观者。常规共享密钥模型不为每一对成员提供相同意义上的独立身份隔离；分发主密钥扩大了成员信任范围。没有主密钥的公共共享节点处于另一个信任位置，不能与同网 R 混称。

## 第三步：安全模式的直连握手怎样建立会话

Noise 是组织密码学握手的协议框架。v2.6.4 的直接节点连接在安全模式中使用 `Noise_XX_25519_ChaChaPoly_SHA256`。名字后面的组合说明密钥协商、握手加密与哈希组件；它不是说后续所有业务包都必须一直采用同一种握手算法。

XX 是三条握手消息的模式。直觉上，双方先交换临时材料，再在握手保护下交换静态身份，并结合 EasyTier 的网络秘密证明、预期公钥或可信凭据来判定认证。仅接收到一个公钥不能证明“这是我预期的人”，协议还需要信任策略。

源码会为结果记录认证层级。例如确认网络秘密与验证预期节点，并不是同一条证据；公共共享节点在没有公钥锁定要求时也可能得到 `EncryptedUnauthenticated`，即“有加密但尚未建立预期身份依据”。因此开启安全模式，不能直接推断所有入口已被可靠认证。

握手处理会话创建、加入或同步，并协商后续数据加密相关信息。Noise 握手与数据包加密要分开看：前者建立可信会话与密钥材料，后者按会话处理持续数据。v2.6.4 还拒绝同网络节点间不一致的安全模式；升级或调整时必须关注双方配置与版本兼容。

## 第四步：经过 R，最终两端仍可建立自己的安全会话

安全模式下，A 需要经 R 联系 B 时，可以使用 `Noise_IK_25519_ChaChaPoly_SHA256` 的中继会话握手。IK 模式要求发起方已知道目标静态公钥；这里的握手消息通过已有路由送到最终目标 B，并不是要求 R 代替 B 拿走它的身份。

这样要区分**相邻连接的保护**与**A—B 最终会话的保护**。R 可以移除自己这一段运输所需的外层处理并继续投递，但不应仅凭与 A、B 各自的相邻连接密钥就取得 A—B 最终会话的明文业务。目标会话公钥来源与验证链仍需正确，密码学不会自动补齐错误配置。

上述 XX 直连与 IK 中继会话均属于 **v2.6.4 的安全模式路径**，不是所有普通 UDP/TCP 连接的必经步骤。WireGuard 协议也使用 Noise 思想，但 EasyTier 的这组私有节点消息不因此变成标准 WireGuard 报文。

## 第五步：认证通过之后才轮到授权

ACL（访问控制列表）根据流量或成员条件决定允许、拒绝等行为；主机防火墙和应用账号又可加自己的限制。允许某人入网不应被理解成允许它访问 B 全部业务，网络认证也不代替网页账号。

v2.6.4 的包处理会在出站及目的端入站路径使用 ACL，入站业务在解密后才能据内层字段检查。规则配置、顺序和生效状态必须核对。安全模式还支持不分发主密钥的凭据节点，涉及可信凭据、公钥、有效期与权限；它是完整成员管理能力，不能靠复制一段密钥文本就认为部署完成。

## 怎样观察：把能力与证据分列

配置中启用加密说明程序意图，连接认证状态说明某次握手结果，业务成功说明这次访问被接受。观察时把它们分列，记录版本、目标和时间。原有接口抓包读不到 HTTP 路径，也可能是应用自身 TLS 加密，不能仅靠“乱码”证明 EasyTier 的全部认证配置。

TUN 上看到明文并不与运输加密矛盾，它位于受保护传输的终点附近。若 B 代理访问 LAN（局域网）设备 H，B—H 是新的保护边界；若应用只用 HTTP，这一段不能被 A—B 的 EasyTier 加密自动覆盖。

## 进阶阅读：数据序号、重放与传输层假定

<details class="advanced">
<summary>握手之外还需要维护安全数据状态</summary>

`secure_datagram.rs` 按方向、会话代次和密钥 epoch 管理数据加密。nonce 包含 epoch 与序号，重放窗口拒绝重复或不合条件的包；成功验证后才提交相应重放状态。重放是重复发送捕获的密文，不能与应用正常重试或内层 TCP 重传混为一谈。

此版本 QUIC 隧道采用 `quinn_plaintext` 配置，不能把标准 QUIC 通常结合 TLS 1.3 的性质直接当作它的内容保护证据。WSS 的客户端使用自定义跳过服务器证书信任链验证的配置；有 TLS 加密也不表示已经通过公共 CA 认证了预期节点。节点身份仍应按 EasyTier 安全模式与可信公钥机制判断。

这些说明是固定源码的行为边界，不是对读者现有实例完成的安全审计。检查应从实际配置与认证结果开始，不能为“验证”而公开主密钥、私钥或完整凭据。

</details>

## 常见误解

“有加密就认对了人”遗漏独立身份依据；“知道主密钥就应该拥有全部应用权限”遗漏授权；“安全模式会给 HTTP 自动加上 HTTPS”混淆两个保护终点；“中继绝不可能看见任何信息”遗漏投递头和元数据，也没有说明它持有什么密钥。

## 两道练习与答案

1. A 开启安全模式并连接了一个未锁定公钥的公共入口。可否仅据此宣布入口就是预期运营者？

<details class="answer">
<summary>查看第 1 题答案</summary>

不能。加密连接与可信身份不同，需要预期公钥或其他可靠信任依据。源码允许部分关系处于加密但未认证的层级，必须检查实际认证状态与配置。

</details>

2. A—B 的节点数据受到保护，B 再用 HTTP 访问 H。谁可以看到 B—H 的明文？

<details class="answer">
<summary>查看第 2 题答案</summary>

B 与 H 的应用及能够观察这一段明文链路的位置可能看见。A—B 的保护在 B 终止，不会自动扩展到 H；需单独选择应用加密或保护 B—H 的通道。

</details>
