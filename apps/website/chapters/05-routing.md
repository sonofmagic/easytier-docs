# 05 · 系统怎样选择下一步，回应怎样回来

## 这一章要解决的问题

A 的浏览器已经选好了目标地址和 `8080` 服务。现在，电脑同时有 Wi-Fi 和虚拟接口，应该把数据交给哪一个？如果送到了 B，为什么 A 仍然可能等不到回答？

这一章要回答：**每台设备怎样选择眼前的下一步，以及为什么回应也需要自己的路线。** 我们先用一张很小的规则表推演，不把真实系统的一长页输出当作第一道题。

## 先回顾两件事

第一，地址范围是一组地址。本章教学条件下，`192.168.10.0/24` 包含 `192.168.10.0` 到 `192.168.10.255`。[第 3 章](/chapters/03-addresses)解释了它不是“已经相连”的证明。

第二，数据送达正确接收程序，程序还要处理并把回应送回来。这是[第 2 章](/chapters/02-packets)的交接链。浏览器要看到结果，不能只完成去程。

需要先找到自己电脑的原有网络 IP 和路由器字段时，可以只读跟随[认识自己的网络](/basics/my-network)。本章用教学地址，不要求把你的配置改成相同数字。

## 一步一步看

### 第一步：区分最终目标和下一站

家中的路由器负责在网络之间继续搬运数据。电脑把不属于眼前这张网络的目标交给它处理时，路由器就是一个**网关**：前往其他网络的下一站。

**下一跳**指当前设备准备把数据交给的下一个接收者。它可以是路由器，不必是提供网页的最终电脑。把包交给路由器，也不表示浏览器突然改成访问路由器的网页。

假设 A 的原有网络 IP 为 `192.168.10.20/24`，这张网络上的路由器为 `192.168.10.1`。它们只是本章模型。路由器 `.1` 是常见配置，并不是所有家庭必须如此。

### 第二步：先查目标属于哪条规则

**路由表**是选择出口和下一站的规则集合。下面先只保留两条教学规则，并假设本地网络实际已经连好：

| 目标范围          | 下一步                             | 在本模型中的意思       |
| ----------------- | ---------------------------------- | ---------------------- |
| `192.168.10.0/24` | 交给本地网络接口，在本地链路找目标 | 属于眼前这张网络的范围 |
| 其他目标          | 先交给路由器 `192.168.10.1`        | 让下一站继续决定怎样送 |

A 访问 `192.168.10.30` 时，第一条匹配，按本地网络处理。访问教学外部地址 `203.0.113.20` 时，第一条不匹配，就交给路由器。这类没有更具体规则时采用的规则叫**默认路由**。

`203.0.113.20` 属于文档保留地址，本章只用于推演，不是真实探测目标。系统通常有比这两条更多的规则；这个表先用来解释每条规则在做什么。

### 第三步：路由器继续选择，不会保证所有目标都能到达

```mermaid
flowchart LR
  A["A<br/>最终目标是远端服务"] -->|"下一站：家中路由器"| G["路由器<br/>继续查询自己的规则"]
  G -->|"模型中存在后续可用路径"| B["远端设备<br/>接收目标请求"]
  B -. 回应需要返回路径 .-> G
  G -.-> A
```

A 不必提前知道沿途每台路由器。它需要知道可用的下一步，后面的设备分别继续查规则。就像把一份物品交给下一处运输站点，站点还要有下一段安排。

类比的边界是：网络选择由地址和规则决定，不是凭工作人员认识收件人。默认路由也不是万能地址查询。把朋友家的私有地址交给家庭路由器，并不会让路由器自动知道“应该送到那个朋友家”。没有后续可用路线，访问仍会失败。

### 第四步：加入虚拟接口这一条选择

现在再假设 A 的系统里有一条匹配 EasyTier 虚拟范围的有效规则：目的为 `10.144.144.0/24` 的包交给 EasyTier 虚拟接口。教学 B 的虚拟 IP `10.144.144.2` 属于这个范围，所以系统应把它交给虚拟接口，而不是按“其他目标”直接交给家庭路由器。

两条规则都能描述这个目标时，更具体的目的范围先使用。这叫**最长前缀匹配**；本章先理解“准确匹配这小段范围的规则，比处理所有其他目标的默认规则更具体”。它不是比较哪条路线物理上更短。

接着，EasyTier 要决定怎样把这份数据送到 B。系统的选择回答“交给哪个接口”，EasyTier 的节点选择回答“从这里怎样到目标节点”。它们不是同一个问题，后者在第 14 章展开。示例 `/24` 不保证与每种实际配置完全相同，应查看实际路由。

### 第五步：沿回应方向再查一次

B 的服务回应 A 时，目标变成 A 的地址。B 的系统需要自己的正确出口，EasyTier 或沿途设备也需要可用的返回连接。A 的规则不会自动替 B 决定这些步骤。

如果请求已经到 B，而 B 把回应交给错误出口，A 仍会等待。**回程**描述的就是返回发起者这条路径。去程与回程不要求每一步都完全对称，但两方向必须实际可用，并符合有关状态与访问规则。

## 先预测，再观察

这里是明确的纸面模型，不执行路由修改。

**先预测。** 在前面的两条表项之外，加上“`10.144.144.0/24` 交给 EasyTier 虚拟接口”。分别判断三个目标的下一步：`192.168.10.30`、`10.144.144.2`、`203.0.113.20`。再问：第三个目标交给路由器，是否已经证明它可以到达？

**再观察。** 在表格上逐个圈出匹配规则：第一个按本地网络，第二个进虚拟接口，第三个先交给路由器。最后一个选择只确定下一站，没有验证后续路径。

**解释。** 规则表依据目的地址作选择。你没有在浏览器里选择“走 Wi-Fi 还是 EasyTier”，系统通过已有规则完成交接。每一步仍需要真正的网络条件支持。

**边界。** 这不是你的真实路由表。若已有 GUI 组网，可对照[实机案例](/cases/local-gui)中“目标路由经 `utun6`”的记录，但其他机器的接口名、前缀和目标都可能不同。查看路由不等于验证服务；不因示例推演而新增、删除或清空现有规则。

## 常见误解

“有默认网关，任何地址都能找到”把默认下一站当作整个互联网的地址保证。网关也需要后续规则和可用路径。

“EasyTier 列表里有 B，应用的包就一定进了 EasyTier”忽略了系统出口。程序知道节点关系，与系统把业务包交给正确接口，是不同证据。

“请求到达 B，访问就完成了”忽略了服务处理和回程。排查时分别记录到达、回应、返回与浏览器结果，能更准确定位等待发生在哪一段。

## 两道练习

1. 模型中到 `10.144.144.0/24` 有专门的虚拟接口规则，同时还有默认路由。访问 B `10.144.144.2` 应选哪条？

<details class="answer">
<summary>第 1 题：使用更具体的目的范围</summary>

选择匹配 `10.144.144.0/24` 的虚拟接口规则，它比默认规则更具体。之后仍需要 EasyTier 把数据送到 B；选对接口不是整个请求成功的证明。

</details>

2. 已观察到请求到达 B，但 B 的回应走向一个不能到达 A 的出口。A 可能看到什么？为什么？

<details class="answer">
<summary>第 2 题：按返回方向重走一次</summary>

A 可能等不到回应并超时。去程成功只说明请求到了 B，回程由 B 及沿途设备自己的规则决定，不能用 A 的成功去程代替返回路径的验证。

</details>

## 进阶阅读

<details class="advanced">
<summary>完整路由匹配、ARP 与两张路由表</summary>

默认 IPv4 路由常写为 `0.0.0.0/0`，零位前缀不限制目标。在同一张普通目的地址路由表中，匹配目标的 `/32` 比 `/24` 更具体，`/24` 比 `/16` 更具体。因此旧 VPN 的 `10.144.144.2/32` 规则可能把本应进 EasyTier 的业务包引向其他出口，即使 EasyTier 本身在线。

前缀相同时，系统还可能使用优先级、度量值等条件；度量值是系统用于比较候选规则的数值。策略路由可以按源地址或其他条件选择表。不能简单说“哪个度量值小，就一定压过所有更具体前缀”。这些细节需按操作系统核对。

在本地 IPv4 以太网链路，发送需要知道眼前接收接口的 MAC 地址。MAC 是链路上的接口地址，与本章的原有网络 IP 不同。ARP（地址解析协议）用于在当前链路问“这个 IP 对应哪个 MAC”。发往外部目标时，A 通常查的是当前网关的 MAC，不是向全互联网询问远端 B 的 MAC。

本地帧可以写网关为链路接收者，而包内的目标 IP 仍是相应层次的最终目标。帧跨链路会重新组织。ARP 广播通常留在当前广播域，即能收到这种本地广播的一组接口；普通路由器不会把它一路广播到异地。

常规 EasyTier TUN 交接 IP 包，不通过以太网 ARP 寻找远端虚拟 IP。系统路由把内层包送进 TUN，EasyTier 的节点路由选择到 B 的路径，外层通信再使用系统的底层网络出口。它们需要协调，但不是一张表。外层若错误地又被送回同一个隧道，可能形成循环。

macOS 路由输出中的某些字段也不能直接解释为 EasyTier 路径跳数。实机案例的系统 `hopcount` 与 GUI 的目标 `p2p` 属于不同观察，详见[案例的证据边界](/cases/local-gui)。

</details>
